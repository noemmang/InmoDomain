# InmoDomain — Contexto y reglas de trabajo

> Este documento resume cómo trabajamos en el proyecto **InmoDomain**, qué decisiones de arquitectura y diseño se han tomado, y qué reglas rigen tanto la forma de explicar las cosas como la forma de escribir código cuando llegue el momento. Está pensado para pegarse al principio de **cualquier conversación nueva** y que la explicación pueda continuar exactamente donde se quedó.

## 1. Objetivo del proyecto

InmoDomain es una plataforma de análisis del mercado inmobiliario español, construida como proyecto de portafolio. Consume datos oficiales del INE (API JSON, tabla 6150) y del MIVAU (ficheros `.XLS` trimestrales), y permite explorar el mercado por provincia, comparar provincias, generar un "Property Score" propio, guardar favoritos y crear alertas.

El objetivo de aprendizaje no es principalmente escribir código a mano: es entender **arquitectura, conceptos y flujos de sistemas** con la profundidad suficiente para poder explicarlos y dirigir con criterio a una IA/agente que sí escriba el código.

## 2. Reglas de trabajo — modo entrega directa (vigente)

> Vigente desde la v35 y hasta que el usuario indique lo contrario (como mínimo hasta llegar a la parte de código puro del frontend, Fase 15). Sustituye al modo explicativo anterior (bloques pequeños, conceptos, decisiones consultadas una a una).

**Cómo se retoma en un chat nuevo**
1. Leer los dos documentos de `docs/`, pero **tomar el estado real del código del repositorio como fuente de verdad**: los documentos pueden ir por detrás. El último bloque hecho es el último que existe en el código, no el último que consta en Progreso.
2. Continuar desde ahí sin preguntar en qué bloque se está ni pedir confirmación.

**Cómo se entrega un bloque**
1. Se entrega el **bloque entero** de una vez: todos los ficheros que se puedan escribir con lo que ya existe.
2. Cada fichero va **en el chat**, con su **ruta completa** y su **contenido íntegro** para pegar. Un fichero existente que cambia se entrega completo, nunca como fragmento.
3. **Sin explicaciones ni justificación de decisiones en el chat.** Las decisiones se toman sin consultar y se registran de forma concisa en Contexto y Progreso. Solo se pregunta ante un bloqueo real: falta un fichero imprescindible que no se puede deducir, un dato externo por verificar, un coste en Azure o un riesgo de seguridad.
4. Tras los ficheros: los **comandos de PowerShell** necesarios (secretos, migraciones, build, pruebas), como comando puro, en un único bloque.
5. Al final: el **commit del bloque** (título + cuerpo breve, con los comandos `git add` y `git commit`) para tener trazabilidad.
6. Cada bloque cierra con **ambos documentos actualizados y completos** (Contexto y Progreso), como ficheros descargables si son largos, nunca como fragmentos. Las entradas nuevas son concisas.
7. Un bloque es una unidad coherente de un servicio o de una fase (por ejemplo, "Notifications"), no una tanda de ficheros sueltos.

**Reglas que siguen vigentes de la etapa anterior**
- Terminal: **PowerShell**. IDE: **Visual Studio Community**.
- Los comandos de terminal se entregan como comando puro, listo para ejecutar.
- **Nunca se añade código de prueba, datos de relleno ni implementaciones simuladas** salvo petición explícita. Si una pieza depende de una fase futura, se deja explícita la carencia (p. ej. con una excepción clara) en vez de esconderla — coherente con la regla de gobernanza nº2.

## 4. Decisiones de arquitectura y diseño (registro vivo)

**Identidad del proyecto**
- Nombre: **InmoDomain**.
- Dominio: ya en propiedad del usuario, fuera del presupuesto de infraestructura del proyecto.

**Presupuesto**
- Objetivo: **≤ 10 €/mes** de infraestructura, presupuesto total y estricto (dominio aparte, ya cubierto).
- Protección: Azure Budget con alertas en 50% / 75% / 90% / 100%, y `maxReplicas = 1` durante el desarrollo.
- Explícitamente **evitados** por coste: Azure SQL, Redis gestionado, Application Gateway, NAT Gateway, Load Balancer dedicado, AKS, Azure Front Door, Log Analytics con retención alta, ACR, **Private Endpoint de Container Apps** (~0,10 €/hora, ~73 €/mes — no confundir con el ingress interno, que es gratuito y sí se usa).

**Backend**
- Runtime: **.NET 10 SDK**. Se descarta .NET Framework, .NET Standard, ASP.NET clásico y EF6.
- Framework web: **ASP.NET Core**. ORM: **EF Core** con proveedor PostgreSQL.
- API Gateway: **YARP** como único punto de entrada público; el frontend nunca llama directamente a un microservicio.
- **Arquitectura interna de cada microservicio**: patrón en capas — **Controller → Service → Repository**, con **DTOs** en el límite HTTP (entrada/salida de cada Controller) y **entidades** (`Models/`) como reflejo de las tablas, separadas de los DTOs. El Controller no conoce la base de datos; el Repository no conoce reglas de negocio; el Service no conoce HTTP ni el motor de base de datos concreto. Se usan interfaces (`IProvinceService`, `IProvinceRepository`, etc.) para permitir inyección de dependencias y facilitar tests. **No se usan clases base compartidas entre entidades** (nada de `BaseEntity`) salvo que una necesidad concreta lo justifique más adelante.
- **Nomenclatura de entidades y DTOs**: en **inglés**, igual que rutas y JSON (coherente con que son código visible), reservando el español exclusivamente para nombres de tabla/columna en la base de datos.
- **Manejo de fallos de negocio en los Services**: se usa un tipo `Result` / `Result<T>` (en `Common/`) en vez de excepciones para casos de fallo esperados y previsibles (no encontrado, conflicto, etc.). Los Services devuelven `Result`/`Result<T>` cuando la operación puede fallar de una forma que el Controller necesita distinguir; si una operación no tiene ningún caso de fallo de negocio posible (p. ej. un listado simple), se devuelve el valor directamente sin envolver. El Controller traduce `ResultError` al código HTTP correspondiente (`NotFound`, `Conflict`, etc.). Comprobar propiedad de un recurso (¿es de este usuario?) y no encontrarlo se tratan como el mismo `ResultError.NotFound`, para no filtrar la existencia de recursos ajenos.

**Microservicios iniciales** (responsabilidad única, base de datos lógica propia, sin tablas compartidas):
1. **Identity** — autenticación (login, registro, JWT, recuperación de contraseña)
2. **Property** — entidades geográficas (provincias, favoritos)
3. **Market Data** — única puerta de entrada a fuentes externas (INE, MIVAU); **interno, nunca expuesto por el Gateway**
4. **Analytics** — cálculos, tendencias y el Property Score
5. **Alerts** — reglas definidas por el usuario
6. **Notifications** — envío de avisos

**Base de datos**
- Motor: **PostgreSQL**. Proveedor: **Neon** (Free: scale-to-zero, 100 CU-hours/proyecto/mes, 0,5 GB/proyecto, hasta 100 proyectos).
- **Organización en Neon**: **un único proyecto Neon** (`InmoDomain`) para todo el sistema, con **una base de datos lógica por servicio** dentro de ese proyecto (`property_db`, `market_data_db`, etc.). La cuota gratuita (100 CU-hours, 0,5 GB) se comparte entre todos los servicios, a cambio de una gestión más simple (un solo panel, un solo proyecto que vigilar).
- **Conexión a Neon — patrón pooled/direct**: cada servicio guarda **dos** cadenas de conexión en User Secrets/variables de entorno: una con sufijo `-pooler` en el host (usada por la app en tiempo de ejecución, vía PgBouncer) y otra directa sin `-pooler` (usada exclusivamente para migraciones de EF Core, ya que Neon desaconseja aplicar migraciones a través del pooler).
- **Claves primarias**: toda tabla con una PK propia generada por el sistema usa **`Guid`** (`uuid` en PostgreSQL), nunca enteros autoincrementales. Excepción: cuando existe una **clave natural externa** ya única y estable (el código de provincia del INE), esa clave natural se mantiene como referencia entre servicios en lugar de sustituirse por un Guid — ver más abajo.

**Provincias: Guid interno vs. código INE como referencia entre servicios**
- `provincias` tiene `Id (Guid)` como clave primaria interna de Property, y una columna `codigo_ine (string, único)` con el código oficial de 2 dígitos del INE.
- El **código INE sigue siendo la referencia real entre servicios**: rutas públicas (`GET /api/v1/provinces/{codigoProvincia}`), `favoritos.codigo_provincia`, `alertas.codigo_provincia`, `notificaciones.codigo_provincia` y las tablas de Market Data (`compraventas_vivienda`, `valores_tasados`) siguen usando el código INE como `string`, no el Guid.
- Motivo: el código INE es una clave natural ya única y estable, es el identificador con el que llegan los datos oficiales desde las fuentes externas (INE/MIVAU) y es legible en una URL. Sustituirlo por un Guid obligaría a traducir constantemente entre Guid y código INE en cualquier llamada entre servicios que involucre a Market Data, sin resolver ningún problema real. El Guid de `provincias` queda como identificador interno de Property, sin propagarse al resto del sistema.

**Comunicación entre servicios**
- **Síncrona (HTTP/REST)**: usada cuando un servicio necesita un dato de otro en el momento (p. ej. Alerts validando `codigo_provincia` contra Property al crear/editar, o Analytics combinando datos crudos de Market Data). Se valida contra otro servicio cuando lo exige la integridad del dato, no solo cuando hay riesgo de seguridad.
- **Asíncrona (eventos, Service Bus)**: usada para efectos secundarios que no bloquean la respuesta al usuario (notificaciones, recálculos tras una importación). Ver el registro de eventos de Service Bus en esta misma sección 4 ("Registro de eventos de Service Bus").
- **Excepción documentada — JWT opcional**: el endpoint de ficha de provincia en Analytics (`GET /api/v1/provinces/{codigoProvincia}/analytics`) no exige JWT. Si no hay token, o es inválido, responde igual con los datos base (nunca 401 por esa causa); si el token es válido, añade campos personalizados (p. ej. `isFavorite`, que Analytics resuelve llamando a Property con el JWT reenviado). Es la única ruta pública del proyecto con este comportamiento — se documenta explícitamente para no confundirla con un descuido de seguridad frente al resto de rutas, que son protegidas o públicas de forma binaria.
- **Nota de implementación (resuelta en la Fase 8)**: mientras Identity y la validación de JWT no existían, cualquier Controller que necesitara el `usuario_id` del token lo dejaba explícito con `NotImplementedException`, nunca con un valor simulado. Desde la Fase 8 el `usuario_id` sale siempre del claim `sub` del JWT validado, nunca de la URL ni del body.

**Convenciones de API**
- Rutas y campos JSON en **inglés**; base de datos en **español**.
- Todas las rutas bajo el prefijo **`/api/v1/`**.
- El `usuario_id` de operaciones sobre el propio usuario sale siempre del JWT, nunca de la URL ni del body.

**Caché**
- Tabla de caché dentro de PostgreSQL (`market_data_db.datos_cache`), uso interno de Market Data. No se usa Redis gestionado. Redis queda como posible v2.

**Market Data — integración con fuentes externas**
- **INE**: API JSON del servicio Tempus3, pública, **sin autenticación ni API key**. Endpoint base `https://servicios.ine.es/wstempus/js/ES/DATOS_TABLA/{idTabla}` (tabla **6150**). Filtrado vía parámetro `tv=idVariable:idValor`; con `tip=AM` la respuesta incluye los metadatos de cada serie (necesarios para identificar la provincia). El parámetro `nult=N` permite pedir solo los últimos N periodos, evitando releer la serie completa en cada ejecución del job.
- **Corrección importante, verificada contra respuestas JSON reales de la API**: la tabla 6150 **no publica una serie que cruce régimen y estado** — solo ofrece el desglose por **estado** (nueva / segunda mano) y por **régimen** (libre / protegida) como dimensiones independientes, no combinables en una misma llamada filtrada. Decisión de diseño: se importa únicamente el desglose por **estado**, aceptando que cada valor mezcla régimen libre y protegido (fracción minoritaria del total); la dimensión `regimen` se descarta del esquema y del `ImportJob`. Motivo: se prioriza poder distinguir nueva/segunda mano —relevante para las estadísticas del proyecto— sobre la exclusión exacta de la vivienda protegida.
- **Forma real del JSON de la 6150** (verificada, no asumida): cada serie trae `COD`, `Nombre`, `MetaData[]` (cada entrada con `Id`, `T3_Variable`, `Nombre`, `Codigo`) y `Data[]` (`Fecha` como texto ISO-8601 con offset —no epoch ms—, `T3_TipoDato`, `T3_Periodo`, `Anyo`, `Valor`). La respuesta mezcla niveles geográficos (Nacional, Comunidad Autónoma y Provincia) en el mismo listado, con solapamiento real: las 6 comunidades uniprovinciales (Madrid, Asturias, Cantabria, Murcia, Navarra, La Rioja) aparecen duplicadas, una vez como CCAA y otra como provincia, mismo valor. El cliente debe descartar toda serie cuya `MetaData` no incluya una entrada con `Id` de variable = 115 (Provincias).
- **MIVAU — corrige el diseño inicial de la Fase 2**: la fuente real **no es un CSV**, sino ficheros **`.XLS`** (formato Excel binario antiguo, BIFF), uno por serie, con **URL numérica estable** que no cambia cada trimestre (p. ej. vivienda libre ≤5 años y >5 años como series independientes). Cada fichero tiene 4 hojas (una por bloque de años) que hay que leer todas para la serie completa; cada hoja es una matriz ancha de publicación (territorios anidados en filas, trimestres agrupados por año en columnas), no una tabla "tidy". No incluye código INE, solo el nombre de la provincia en texto libre con formatos variables, y una fila agregada `'Ceuta y Melilla'` además de las filas individuales, que se descarta para no duplicar el dato.
- **Librería de lectura del `.XLS`: `ExcelDataReader`** (MIT, solo lectura, streaming fila a fila, ligera), descartando `NPOI` (Apache 2.0, lectura y escritura, más pesada por cubrir todo el modelo de objetos de Excel) porque el servicio solo necesita leer, nunca escribir el fichero de origen. Requiere registrar `System.Text.Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` una vez al arrancar, ya que los `.xls` antiguos usan páginas de código no registradas por defecto en .NET Core.
- **IDs numéricos del INE**: variable provincia = 115 (52 valores, uno por provincia) — confirmado. Variable estado = 345, valor "nueva" = 16464 — confirmado contra respuesta real; valor "segunda mano" **pendiente de confirmar** (no ha aparecido aún en ninguna muestra de JSON real; no se asume su id sin verlo). Variable régimen = 503, valor "libre" = 284449 — confirmado, pero **ya no se usa** en el `ImportJob` (ver corrección de arriba: el régimen se descarta del diseño); el id de "protegida" queda sin confirmar y sin necesidad de confirmarlo. Catalogados en `IneMetadataCatalog.cs`, movido dentro de `MarketData.ImportJob/Integrations/Ine/` (namespace `MarketData.ImportJob.Integrations.Ine`, coherente con la convención namespace = proyecto + carpeta; antes vivía suelto fuera de cualquier `.csproj` y no compilaba).
- **Diccionario MIVAU → código INE resuelto**: las 52 entradas, verificadas idénticas en las 8 combinaciones fichero × hoja de los dos `.XLS`. Catalogado en `MivauProvinceNames.cs`; el nombre leído del `.XLS` debe pasarse por `Trim()` antes de la búsqueda.
- **Tratamiento de huecos de dato (`'n.r'`)**: el literal `'n.r'` (no representativo) se trata como ausencia de dato para esa provincia+periodo — no se inserta fila ni se lanza excepción.
- **Estrategia de reimportación de MIVAU**: se relee el fichero completo y se hace upsert en cada ejecución del job (volumen total ≈6.700 filas, trivial), en vez de intentar traer solo el trimestre nuevo, ya que el origen no ofrece un mecanismo equivalente al `nult` del INE para pedir "solo lo último".

**Market Data — arquitectura interna**
- El servicio se divide en **tres proyectos**, variante del patrón en capas usado en Property: `MarketData.Data` (biblioteca con el `DbContext`, las entidades y el `DbContextFactory` de diseño para migraciones), `MarketData.Api` (API de solo lectura, patrón Controller → Service → Repository, protegida con `ApiKeyMiddleware` en vez de JWT, coherente con que este servicio nunca pasa por el Gateway) y `MarketData.ImportJob` (proyecto de consola, sin API — escribe directamente contra `market_data_db` con su propio `DbContext`, referenciando `MarketData.Data`, sin pasar por `MarketData.Api`). Motivo de la división en tres proyectos en vez de uno solo: `MarketData.Data` se comparte entre `MarketData.Api` (lectura) y `MarketData.ImportJob` (escritura) sin que ninguno dependa del otro.

**Secretos en desarrollo local**
- Las cadenas de conexión y demás secretos de cada servicio se guardan con **User Secrets** de .NET (`dotnet user-secrets`), nunca en `appsettings.json`. En producción (Azure Container Apps) se usan variables de entorno/secretos de Container Apps — el mecanismo cambia entre entornos, la regla de "nunca en el código fuente" no. Cuando un servicio se divide en varios proyectos (caso Market Data), cada proyecto guarda sus propios secretos bajo su propio `UserSecretsId`: el proyecto con el `DbContextFactory` guarda la cadena de migraciones, el proyecto ejecutable (Api o Job) guarda la cadena pooled de runtime.

**Herramientas de EF Core**
- `dotnet-ef` se instala como **herramienta local** (`dotnet tool install --local`), con su versión fijada en `.config/dotnet-tools.json` en la raíz del repositorio, para que cualquier máquina que clone el proyecto use la misma versión sin pasos manuales adicionales.

**Analytics — cálculo de índices**
- `indice_precio` e `indice_actividad` se calculan y persisten en **dos variantes** por provincia y periodo: **percentil histórico** (la provincia comparada contra su propia serie temporal) y **ranking nacional** (la provincia comparada contra el resto de provincias en el mismo periodo). El frontend muestra el percentil histórico por defecto, con un botón para alternar a ranking nacional — ambas variantes viven precalculadas en la misma fila de `property_scores`, sin ninguna petición de red nueva al pulsar el botón.
- Motivo de precalcular también el ranking nacional en vez de calcularlo al vuelo en la petición: aunque en apariencia es barato de calcular (no necesita historia, solo comparar un periodo entre provincias), la consulta que necesita — "todas las provincias de un periodo" — no es la misma que ya trae la ficha de provincia desde Market Data de forma síncrona ("una provincia, todo su histórico"); calcularlo en el momento de servir la ficha añadiría una llamada nueva y más pesada en cada petición, se pida o no esa vista. Los eventos `ComprasVentasImportadas`/`PreciosImportados` ya entregan el lote completo de provincias de un periodo, así que el ranking nacional se calcula en ese mismo lote de recálculo, junto al percentil histórico, y ambos quedan disponibles con una única lectura a `property_scores`, sea cual sea la vista que pida el frontend.
- `indice_tendencia_precio` no tiene variante de ranking nacional: por definición mide variación en el tiempo, no un nivel comparable entre provincias en un instante dado — necesita mirar historia sí o sí.
- El `property_score` combinado (y las alertas de tipo `property_score`) usan siempre el **percentil histórico** de `indice_precio`/`indice_actividad`, nunca el ranking nacional: es la única variante persistida y estable en el tiempo — el ranking nacional puede cambiar de valor sin que nada cambie en la provincia, si otra provincia se mueve más, lo cual no es un comportamiento adecuado para disparar una alerta.
- Motivo de elegir ranking nacional (y no percentil histórico) como base de `indice_precio`/`indice_actividad` en un proyecto recién nacido: `MarketData.ImportJob` acumula historia poco a poco desde que empezó a correr (arranque en frío, todavía pocos periodos reales por provincia), y un percentil histórico necesita bastantes periodos acumulados para ser fiable; un ranking nacional no tiene ese problema porque compara todas las provincias entre sí en el mismo periodo, aunque solo haya uno importado. Además encaja de forma directa con el comparador de provincias (`GET /api/v1/analytics/compare`), que ya es por definición una comparación entre provincias.
- **Columnas concretas en `property_scores`**: `indice_precio` e `indice_actividad` (ya existentes) pasan a representar explícitamente el percentil histórico; se añaden `indice_precio_ranking_nacional` e `indice_actividad_ranking_nacional` para la variante ranking nacional. `indice_tendencia_precio` y `property_score` no cambian de nombre (ver fórmulas concretas más abajo). La restricción única sigue siendo `(codigo_provincia, periodo)`.
- **Fórmula de percentil histórico y de ranking nacional**: en ambos casos, percentil (0-100) con interpolación lineal estándar — en percentil histórico, la posición del valor actual dentro de la serie histórica propia de la provincia acumulada hasta ese periodo; en ranking nacional, la posición de esa provincia dentro de los valores de todas las provincias en ese mismo periodo. `property_score` es la media simple de `indice_precio`, `indice_actividad` (ambos en su variante percentil histórico) e `indice_tendencia_precio` — los tres pesan igual.
- **`indice_tendencia_precio` — mismo patrón "por defecto + botón" que percentil/ranking, más una tercera vía flexible**: se persisten **dos** variantes, calculadas y guardadas en el mismo recálculo por evento que el resto de índices — `indice_tendencia_precio` (variación frente al **trimestre anterior**, QoQ; sigue siendo la variante por defecto en el frontend y la única que alimenta `property_score` y las alertas de tipo `indice_tendencia_precio`, por el mismo motivo de estabilidad que ya se aplicó al elegir el percentil histórico como base de esas dos cosas) e **`indice_tendencia_precio_interanual`** (nueva columna: variación frente al **mismo trimestre del año anterior**, YoY; vista alternativa mediante botón, `null` mientras la provincia no acumule los 4+ periodos que necesita). Además, para explorar libremente ("máxima cantidad de información" es el objetivo del proyecto), la ficha de provincia acepta un parámetro opcional `trendQuarters` que calcula la tendencia frente a **N trimestres atrás, el N que pida el frontend**, en el momento de la petición — sin violar el principio de "nada calculado en vivo" fijado para el ranking nacional: esa regla existía porque el ranking necesita una consulta de forma distinta a la ya existente (todas las provincias de un periodo, no una); calcular una tendencia a N periodos, en cambio, es la misma consulta que la ficha de provincia ya hace sobre su propio histórico en `property_scores` (una provincia, sus propios periodos), así que no añade ninguna consulta nueva ni más cara — solo resta dos valores ya disponibles o, como mucho, un único `SELECT` adicional por clave única `(codigo_provincia, periodo)` si el periodo pedido cae fuera del rango `from`/`to` ya solicitado. Si no hay suficiente historia para el `N` pedido, se devuelve explícitamente "sin datos suficientes", nunca un valor inventado. Esta variante por `trendQuarters` nunca alimenta `property_score` ni las alertas, solo las dos variantes persistidas lo hacen.

**Analytics — Service Bus**
- El consumidor de los eventos `ComprasVentasImportadas`/`PreciosImportados` se implementa ya en esta fase con el SDK real de Azure Service Bus (`Azure.Messaging.ServiceBus`), aunque el **namespace real de Azure** todavía no existe en el proyecto — llega en la Fase 14 (despliegue). Hasta entonces, el consumidor falla con un error de conexión claro al arrancar si no encuentra un broker real al otro lado, nunca con una implementación simulada que finja recibir eventos.
- **Desarrollo local (verificado, sin coste)**: se usa el **emulador oficial de Azure Service Bus** (imagen Docker `mcr.microsoft.com/azure-messaging/servicebus-emulator`, con un contenedor de SQL Server Linux como dependencia obligatoria del propio emulador), levantado con `docker compose` junto al resto del entorno local. El emulador expone colas/topics/suscripciones reales a través del mismo SDK (`Azure.Messaging.ServiceBus`) y de una cadena de conexión estática, sin ningún coste de Azure al ser 100% local. Los topics `ComprasVentasImportadas`/`PreciosImportados` y su suscripción para Analytics se declaran en un `Config.json` que se monta en el contenedor del emulador. Con esto, el consumidor siempre tiene un broker real al que conectarse en desarrollo (el emulador), y solo falla con el error explícito de conexión si ni el emulador ni un namespace real están disponibles — nunca se relaja la regla de "nunca simulado", solo cambia qué broker real hay al otro lado según el entorno (emulador en local, namespace real de Azure en producción).

**Analytics — arquitectura interna**
- **Un solo proyecto** (`Analytics`, mismo patrón en capas que Property: Controller → Service → Repository), en vez del split en varios proyectos usado en Market Data. El consumidor de Service Bus vive como un `BackgroundService` dentro del mismo proceso que la API. Motivo de no replicar aquí el split de Market Data: el riesgo que justificaba separar en varios proyectos —que un fallo de conexión del consumidor tumbe también la API pública de lectura— queda resuelto por el emulador de Service Bus (ver punto anterior): en desarrollo local el consumidor siempre encuentra un broker real (el emulador) y arranca sin problema; la decisión sobre cómo aislar ese riesgo en producción (Fase 14) se revisa en su momento, cuando exista el namespace real.

**Identity — endpoints y arquitectura interna**
- 9 endpoints: `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/forgot-password`, `POST /api/v1/auth/reset-password`, `GET /api/v1/auth/me`, `PUT /api/v1/auth/me`, `PUT /api/v1/auth/me/password`. Sustituye a los "7 endpoints" mencionados en la Fase 2, nunca detallados en su momento — el recuento sube a 9 al cerrar el diseño de los refresh tokens.
- **Un solo proyecto** (`backend/Identity/Identity.csproj`, mismo patrón en capas que Property: Controller → Service → Repository), no un split como en Market Data: Identity no tiene fuentes externas que importar ni un consumidor de Service Bus (solo publica un evento, no consume ninguno).
- `Common/ResultError.cs` de Identity añade un caso propio, `Invalid`, junto a los ya existentes `None`/`NotFound`/`Conflict`: cubre credenciales incorrectas en login, tokens inválidos/caducados/revocados (`refresh`, `reset-password`) y contraseña actual incorrecta en el cambio autenticado — casos que no encajan como "no encontrado" ni "conflicto".

**Identity — autenticación y tokens**
- Hash de contraseñas: `PasswordHasher<TUser>` de `Microsoft.Extensions.Identity.Core`, usado en solitario (sin adoptar el resto del framework de ASP.NET Core Identity con roles/cookies). No requiere paquete NuGet explícito: ya llega con `Microsoft.NET.Sdk.Web`, el mismo SDK que ya usan Property/Analytics.
- JWT firmado con **RS256** (asimétrico), no HS256 (simétrico): con HS256 los 6 servicios compartirían el mismo secreto, y la fuga del de cualquiera de ellos permitiría falsificar tokens válidos para todo el sistema; con RS256 solo Identity guarda la clave privada, el resto de servicios (a partir de Fase 9) solo necesita la clave pública para verificar. Emisión con `JsonWebTokenHandler` (paquete `Microsoft.IdentityModel.JsonWebTokens`), la recomendación actual de Microsoft frente al más antiguo `JwtSecurityTokenHandler`; llega junto con `Microsoft.AspNetCore.Authentication.JwtBearer`, necesario porque Identity también valida el JWT en sus propios endpoints protegidos (`/me`, `/me/password`).
- Claims del JWT: únicamente `sub` (`usuario_id`), `email`, `iat`, `exp` — sin roles, tal como se cerró en la Fase 2. Issuer `InmoDomain.Identity`, audience `InmoDomain` (compartida por todos los servicios), en `appsettings.json` por no ser secretos — **confirmados por el usuario**.
- Par de claves RS256 (2048 bits) generado una única vez con un script de un solo archivo usando *file-based apps* de .NET 10 (`dotnet run generate-keys.cs`, sin crear un proyecto ni depender de OpenSSL), fuera del repo. Se exportan como base64 de la clave DER cruda (no PEM), para poder pegarlas en un único `dotnet user-secrets set` sin problemas de saltos de línea. La clave privada vive solo en los User Secrets de Identity (`Jwt:PrivateKey`); la pública se reserva aparte, sin usarse todavía, hasta que el resto de servicios empiecen a validar JWT (Fase 9 en adelante).
- Expiración: access token 15 minutos, refresh token 30 días.
- Refresh tokens con **tabla dedicada** `refresh_tokens` en `identity_db` (no columnas en `usuarios`), para permitir varias sesiones/dispositivos simultáneos. **Rotación en cada uso**: cada llamada a `/refresh` revoca el token recibido (`fecha_revocado`) y emite uno nuevo junto con el JWT nuevo — más seguro que un refresh token reutilizable; la reutilización de un token ya revocado como señal para revocar todas las sesiones del usuario queda anotada como mejora futura, no implementada en esta fase para no ampliar el alcance.
- `token_recuperacion` (en `usuarios`) y `token_hash` (en `refresh_tokens`) se hashean con **SHA-256**, no con `PasswordHasher`: son tokens de alta entropía generados por el propio servidor, no contraseñas de baja entropía elegidas por una persona, así que no aporta nada pagar el coste de CPU de un KDF lento como PBKDF2 — sí tiene sentido para las contraseñas de usuario, no para estos.

**Identity — recuperación de contraseña y evento de notificación**
- El email con el enlace de `forgot-password` lo envía Identity **directamente contra Resend** (verificado: nivel gratis de 3.000 emails/mes, 100/día, sin coste), de forma síncrona dentro del propio endpoint — no pasa por Notifications ni por Service Bus. Motivo: `notificaciones.tipo` no contempla este caso (y no tiene sentido que lo haga: es una acción de seguridad puntual con enlace de un solo uso, no un aviso in-app con `leida`/`oculta`).
- Nuevo evento de Service Bus **`ContrasenaCambiada`** (sobre: `id_evento`, `tipo_evento`, `fecha_ocurrencia`, `usuario_id` — mismo patrón que `ComprasVentasImportadas`/`PreciosImportados`, sin acentos/ñ en el nombre por coherencia), publicado por Identity al completar `reset-password` con éxito — distinto del email de Resend: el email lleva el enlace para restablecer, el evento se dispara después, cuando la contraseña ya ha cambiado de verdad, como aviso de seguridad. Sin ningún suscriptor todavía (Notifications no existe, Fase 10 sin empezar) — en Azure real un topic sin suscripciones no da error (descarta el mensaje), pero **el emulador exige al menos una suscripción por topic**, por eso `Config.json` define la suscripción `notifications` (reservada para el futuro consumidor). Cuando llegue la Fase 10 se decidirá el `tipo` correspondiente a añadir en `notificaciones` y su consumidor — el esquema de Notifications no se considera cerrado de antemano, se amplía según las necesidades reales que vayan apareciendo.
- El emulador de Service Bus se **mueve de `backend/Analytics/ServiceBus-Emulator/` a `servicebus-emulator/` en la raíz del repositorio** (carpeta neutra, sin código): dejó de tener sentido vivir dentro de un servicio concreto en cuanto Identity también publica contra él. Ningún código cambia (`ServiceBusEventConsumer` de Analytics y `ServiceBusEventPublisher` de Identity solo usan `ConnectionStrings:ServiceBus`, nunca una ruta de carpeta), solo dónde se levanta `docker compose` en local. `Config/Config.json` recibe el topic nuevo `ContrasenaCambiada` (con la suscripción `notifications`, obligatoria en el emulador).

**Identity — validación, privacidad y resiliencia (Bloque 7)**
- **Validación de entrada en los Dtos** con DataAnnotations, resuelta por el `[ApiController]` (400 automático), sin validación manual en Controllers ni Services. Política de contraseña: **mínimo 8 y máximo 128 caracteres** al fijar una contraseña nueva (`register`, `reset-password`, `me/password`); en `login` y en la contraseña actual de `me/password` solo se exige presencia.
- **`forgot-password` responde siempre 204**, exista o no el email, y aunque falle el envío por Resend (el error se registra con `ILogger` sin incluir el email): evita enumerar qué cuentas existen.
- **Publicación de eventos best-effort tras una operación ya consumada**: si `ContrasenaCambiada` no puede publicarse (Service Bus caído), `reset-password` y `me/password` registran el error y responden 204, porque la contraseña ya cambió y las sesiones ya se revocaron; un 500 en ese punto sería engañoso y llevaría al usuario a reintentar con un token ya consumido. Criterio general para el resto de servicios: un efecto secundario asíncrono no debe tumbar una operación ya persistida.
- **Clientes de mensajería perezosos**: un cliente externo (Service Bus, etc.) inyectado como dependencia de un servicio no debe fallar en su constructor por configuración ausente, porque tumbaría todos los endpoints que dependen de ese servicio aunque no usen el cliente. La creación y la validación de la configuración se difieren al primer uso, dentro del camino que ya tolera el fallo (`ServiceBusEventPublisher` de Identity).
- **Resend**: el `HttpClient` tipado envía siempre `User-Agent` (Resend responde 403/1010 sin él). El remitente de pruebas `onboarding@resend.dev` solo entrega al email de la propia cuenta de Resend; dominio propio verificado en la Fase 14.
- **Entorno local**: cada servicio ejecutable necesita su `Properties/launchSettings.json` con `ASPNETCORE_ENVIRONMENT=Development`; sin él `dotnet run` arranca en `Production` y los User Secrets no se cargan. Puertos locales: Identity `5071`, Analytics `5041`, Market Data API `5111`, Property `5081`, Alerts `5091` (Notifications `5101` propuesto, sin crear todavía).

**API Gateway (Fase 9)**
- **Tecnología: YARP** (`Yarp.ReverseProxy`, proyecto `backend/Gateway`, `net10.0`, `http://localhost:5001` en local), el reverse proxy oficial de Microsoft para .NET. Descartados Ocelot y un gateway propio con minimal APIs: YARP encaja con la pila, se configura por `appsettings.json` y no obliga a mantener código de proxy.
- **Validación del JWT en el Gateway**: valida firma RS256, `iss`, `aud` y caducidad con la **clave pública** (`Jwt:PublicKey`, User Secrets), con `ValidAlgorithms` fijado a RS256, `ClockSkew` 30 s y `MapInboundClaims = false` (mismos parámetros que Identity). Acepta la clave como RSAPublicKey (PKCS#1) o SubjectPublicKeyInfo (X.509). **El Gateway nunca tiene la clave privada.** La validación del Gateway no sustituye a la de cada servicio: se mantiene el zero trust (cada servicio valida el token por su cuenta); el Gateway solo corta antes las peticiones sin token válido.
- **La clave pública se deriva de `Jwt:PrivateKey` de Identity, no se pega a mano**: la reservada en la Fase 8 no coincidía con la privada en uso y el Gateway rechazaba tokens válidos con 401. Procedimiento: script de un solo archivo (`derive-public.cs`, `ImportRSAPrivateKey` + `ExportRSAPublicKey`, base64 DER) y el mismo valor en los User Secrets de Gateway, Property y Analytics (`Jwt:PublicKey`). Los servicios leen los secretos al arrancar: hay que reiniciarlos tras cambiarlos.
- **Políticas de autorización de YARP**: `anonymous` (ruta pública) y `authenticated` (`RequireAuthenticatedUser`), referenciadas por cada ruta en `ReverseProxy:Routes`. Cualquier ruta que no esté declarada responde 404 desde el propio Gateway.
- **Tabla de rutas (20: 14 de la Fase 9, 2 de Alerts y 4 de Notifications)**. Identity (5071): públicas `POST auth/register`, `auth/login`, `auth/refresh`, `auth/logout`, `auth/forgot-password`, `auth/reset-password`; protegidas `GET/PUT auth/me`, `PUT auth/me/password`. Property (5081): públicas `GET provinces` y `GET provinces/{provinceCode}`; protegidas `GET/POST favorites` y `DELETE favorites/{id}`. Analytics (5041): públicas `GET provinces/{provinceCode}/analytics` (JWT opcional, ver excepción en la sección de autenticación) y `GET analytics/compare`. Alerts (5091): protegidas `GET/POST alerts` y `PUT/DELETE alerts/{id}`. Notifications (5101): protegidas `GET notifications`, `PUT notifications/{id}/read`, `PUT notifications/read-all` y `DELETE notifications/{id}`. Todas bajo `/api/v1/`.
- **No expuesto por el Gateway (404 verificado)**: todo Market Data (`/api/v1/property-sales`, `/api/v1/appraised-values`), todo `/internal/*` de Analytics (`metric-value`) y los `/swagger` de cada servicio. Los servicios internos solo se hablan entre sí con `X-Internal-Api-Key`.
- **Rate limiting**: política `auth`, ventana fija por IP, 10 peticiones por 60 s (`RateLimiting:Auth:PermitLimit`/`WindowSeconds` en `appsettings.json`), aplicada a `register`, `login`, `refresh`, `forgot-password` y `reset-password`; `logout` sin limitador. Respuesta 429. Verificado: diez 401 y 429 desde el undécimo intento.
- **CORS**: política `frontend` con los orígenes de `Cors:AllowedOrigins` (hoy solo `http://localhost:3000`), cualquier cabecera y método. El preflight de un origen permitido responde 204 con `Access-Control-Allow-Origin`; el de un origen no listado responde 204 sin esa cabecera.
- **`isFavorite` en la ficha de provincia**: la ruta es anónima en el Gateway, que reenvía la cabecera `Authorization` tal cual; Analytics valida el token (opcional) y, si es válido, llama **directamente a Property** (`PropertyApi:BaseUrl`, sin pasar por el Gateway) a `GET /api/v1/favorites` con el JWT reenviado. El token se lee de la cabecera `Authorization` y no con `GetTokenAsync`, porque el JwtBearer no tiene `SaveToken`. Si Property falla, la ficha responde igual con `isFavorite: null` (ruta pública, no debe romperse por la personalización). El nombre real del campo en el JSON es `isFavorite` (no `esFavorita`).
- **Clave interna Analytics → Market Data**: `MarketDataApi:ApiKey` (Analytics) y `Security:InternalApiKey` (Market Data) deben tener exactamente el mismo valor; si difieren, Market Data responde 401 y la ficha de provincia de Analytics responde 500.
- **Pruebas desde PowerShell 5.1**: `curl.exe` con JSON entre comillas dobles escapadas (`\"`) envía las barras literales y da 400; `-SkipHttpErrorCheck` no existe en 5.1. Las pruebas del Gateway usan `Invoke-RestMethod`/`Invoke-WebRequest` con `ConvertTo-Json` y `try/catch` para leer el código de error.

**Registro de eventos de Service Bus**
- Todos los sobres son JSON con campos en español (`JsonPropertyName`), nombre del evento sin acentos ni ñ, y llevan siempre `id_evento`, `tipo_evento` y `fecha_ocurrencia`. Cada servicio declara su propia copia del sobre (no hay proyecto compartido). El emulador exige al menos una suscripción por topic (`servicebus-emulator/Config/Config.json`).
- **`ComprasVentasImportadas`** y **`PreciosImportados`** — sobre: `id_evento`, `tipo_evento`, `fecha_ocurrencia`, `periodo`, `codigos_provincia`. Consumidor: Analytics (suscripción `analytics`). Publicador: `MarketData.ImportJob` (Fase 11), un evento por periodo con cambios.
- **`ContrasenaCambiada`** — sobre: `id_evento`, `tipo_evento`, `fecha_ocurrencia`, `usuario_id`. Publicador: Identity (`reset-password` y `me/password`). Consumidor: Notifications (suscripción `notifications`).
- **`IndicesRecalculados`** — sobre: `periodo` (inicio del trimestre recalculado) y `codigos_provincia` (solo las provincias que Analytics realmente guardó en ese recálculo). Publicador: Analytics, tras persistir. Consumidor: Alerts (suscripción `alerts`).
- **`AlertaDisparada`** — sobre: `id_alerta`, `usuario_id`, `codigo_provincia`, `metrica`, `condicion`, `umbral`, `valor`, `periodo`. Publicador: Alerts. Consumidor: Notifications (suscripción `notifications`).

**Alerts (Fase 10)**
- **Las alertas se evalúan por evento, no por sondeo ni al importar**: Alerts no escucha `ComprasVentasImportadas`/`PreciosImportados`, porque Analytics recalcula de forma asíncrona sobre esos mismos eventos y Alerts podría leer `metric-value` antes de que terminara (valor del trimestre anterior, disparo erróneo). Analytics publica `IndicesRecalculados` al terminar de persistir y Alerts solo escucha ese. Criterio general: cada servicio publica cuando *su* trabajo está hecho, no cuando empezó el de otro.
- **Una alerta dispara una vez por periodo de dato**: se compara el periodo que devuelve `metric-value` (no el del evento) con `alertas.periodo_ultimo_disparo`, y no dispara si este ya es igual o posterior. Motivo: cada mes de INE refina la misma fila trimestral, y `precio_m2` sale de Market Data con su propio último periodo. Descartados "solo al cruzar el umbral" (exige guardar el estado anterior) y "cada vez que se cumple" (avisos repetidos). Un valor `null` o un 404 de `metric-value` no se evalúan. Solo se evalúan las alertas con `activa = true`.
- **Editar una alerta reinicia `periodo_ultimo_disparo`** si cambia la provincia, la métrica, la condición o el umbral (equivale a una alerta nueva; quien cambia el umbral espera que se evalúe la condición nueva). Editar solo `activa` no lo reinicia, y `fecha_ultimo_disparo` se conserva como histórico. `mayor_que` y `menor_que` son comparaciones estrictas.
- **Rutas** (protegidas, `usuario_id` del claim `sub`): `GET`, `POST`, `PUT {id}` y `DELETE {id}` bajo `/api/v1/alerts`. Provincia inexistente o cuerpo inválido → 400; alerta duplicada (mismo usuario, provincia, métrica, condición y umbral) → 409; alerta ajena o inexistente → 404; Property caído → 503. No hay índice único en BD para las duplicadas (carrera teórica entre dos peticiones simultáneas, con efecto de un aviso doble).
- **Llamadas entre servicios**: a Property (`GET /api/v1/provinces/{code}`, ruta pública, sin reenviar JWT) para validar la provincia; a Analytics (`GET /internal/v1/metric-value`, directo, sin Gateway) con `X-Internal-Api-Key`. **`AnalyticsApi:ApiKey` (Alerts) y `Security:InternalApiKey` (Analytics) deben tener exactamente el mismo valor**; si difieren, Analytics responde 401 y las alertas no se evalúan. Ambos clientes con timeout de 10 s.
- **Publicación en dos sentidos, con criterios distintos**: `IndicesRecalculados` es best-effort (si Service Bus falla se registra y el mensaje original se completa, porque el recálculo ya está guardado; consecuencia: Alerts no evaluaría ese recálculo). `AlertaDisparada` se publica **antes** de marcar la alerta (si falla, la alerta sigue pendiente y el mensaje se reintenta hasta 10 veces, luego dead-letter; perder el aviso sería peor que duplicarlo), lo que da **entrega al menos una vez**: un consumidor de `AlertaDisparada` debe tolerar duplicados.
- **Alcance de Notifications en la Fase 10**: tipos `alerta` (desde `AlertaDisparada`) y `contrasena_cambiada` (desde `ContrasenaCambiada`; obliga a ampliar el `CHECK` de `notificaciones.tipo`). `bienvenida` (exige que Identity publique un `UsuarioRegistrado` inexistente) y `precio_actualizado` (exige un endpoint interno nuevo en Property con los usuarios por provincia favorita) quedan aplazados y siguen en el `CHECK` sin generarse. Sigue abierta la decisión de si Notifications envía además correo (Resend solo entrega a la cuenta de pruebas hasta tener dominio verificado en la Fase 14).

**Notifications (Fase 10, Bloque 6)**
- **Proyecto** `backend/Notifications` (`Notifications.csproj`, un solo proyecto con el mismo patrón en capas que Alerts; consumidor de Service Bus como `BackgroundService` en el mismo proceso), puerto local **5101**, base lógica `notifications_db` en el proyecto Neon `InmoDomain`, secretos `ConnectionStrings:Notifications` (pooled) y `ConnectionStrings:NotificationsMigrations` (directa).
- **Esquema `notificaciones`**: `id` uuid PK, `usuario_id` uuid sin FK, `tipo`, `titulo` (150), `mensaje` (500), `codigo_provincia` nullable (2), `leida` default false, `oculta` default false (borrado lógico), `fecha_envio` y **`clave_deduplicacion` varchar(100) nullable con índice único** (columna nueva de este bloque). `CHECK` de `tipo`: `bienvenida`, `alerta`, `precio_actualizado`, **`contrasena_cambiada`** (ampliado); `bienvenida` y `precio_actualizado` siguen sin generarse.
- **Consumidores** (suscripción `notifications`): `AlertaDisparada` → notificación `alerta`; `ContrasenaCambiada` → notificación `contrasena_cambiada`. Un fallo al procesar deja el mensaje para reintento (hasta 10 entregas, luego dead-letter).
- **Deduplicación** por la entrega al menos una vez de `AlertaDisparada`: clave `alerta:{id_alerta}:{periodo}` (el `id_evento` cambia en cada publicación, así que no sirve como clave) y `contrasena_cambiada:{id_evento}`. Se comprueba antes de insertar y se tolera la violación del índice único (mensaje ya procesado = éxito).
- **Texto de la notificación**: se compone en Notifications a partir del sobre. El nombre de la provincia se resuelve con `GET api/v1/provinces/{code}` de Property (ruta pública, directa, timeout 10 s); si Property falla o no devuelve la provincia, se usa `provincia {código}` y la notificación se crea igualmente. El periodo se muestra como trimestre (`2T 2026`).
- **Sin correo**: Notifications no envía email en esta fase (Resend solo entrega a la cuenta de pruebas hasta tener dominio verificado en la Fase 14); se retoma entonces.
- **Rutas** (protegidas, `usuario_id` del claim `sub`): `GET /api/v1/notifications` (no ocultas, de la más reciente a la más antigua; `unreadOnly` opcional, `limit` 1-100, 50 por defecto), `PUT /api/v1/notifications/{id}/read` (204/404), `PUT /api/v1/notifications/read-all` (204) y `DELETE /api/v1/notifications/{id}` (borrado lógico, 204/404). Una notificación ajena, inexistente u oculta responde 404.

**Market Data ImportJob — publicación de eventos (Fase 11, Bloque 1)**
- Tras cada importación, el job publica **un evento por periodo con cambios reales** (filas insertadas o con valor distinto), con `codigos_provincia` solo de las provincias afectadas: `ComprasVentasImportadas` (periodo mensual, INE) y `PreciosImportados` (periodo trimestral, MIVAU). Una ejecución sin cambios no publica nada.
- **Cada etapa es independiente**: importar compraventas y publicar, e importar precios y publicar. Si una etapa falla, la otra se ejecuta igualmente y el proceso termina con código de salida 1.
- **Publicación tras guardar** (Analytics lee de `market_data_db` a través de Market Data API al recibir el evento). Limitación asumida: si la publicación falla, los datos ya están guardados y la siguiente ejecución, al ser idempotente, no los detecta como cambios; el job lo registra como error y sale con código 1 para que el planificador lo señale. Recuperación manual: borrar las filas del periodo afectado y repetir la ejecución.
- `ServiceBusEventPublisher` del job es perezoso (cliente y senders por topic creados en la primera publicación); secreto `ConnectionStrings:ServiceBus` en los User Secrets de `MarketData.ImportJob`. La programación periódica del job (Azure Container Apps Jobs) queda para la Fase 14.
- `MarketData.ImportJob/Properties/launchSettings.json` con `DOTNET_ENVIRONMENT=Development`: sin él `dotnet run` arranca en `Production` y los User Secrets no se cargan.

**Contenedores (Fase 12, Bloque 1)**

Debian y no Alpine, para evitar problemas de ICU/globalización. Tags y comportamiento verificados por búsqueda web: puerto 8080 por defecto desde .NET 8 y usuario no root.

## 5. Reglas de gobernanza para el código

1. **Seguridad e integridad de datos por encima de cualquier atajo visual o de conveniencia.**
2. **Los errores se resuelven en su causa raíz, nunca se esconden.**
3. **Ninguna información sensible se escribe nunca en el código fuente ni se sube al repositorio** — variables de entorno o gestores de secretos, reflejado en `.gitignore`.
4. **Los comentarios en el código describen qué hace ese fragmento, no explicaciones didácticas dirigidas al usuario.** Esta regla se extiende también a todos los archivos del repositorio, no solo a código C# (por ejemplo, `.gitignore`, `README.md`).
5. Priorizar código correcto y mantenible sobre soluciones rápidas que generen deuda técnica innecesaria.
6. **Toda carpeta del monorepo que exista sin archivos dentro lleva un `.gitkeep`.** Git no versiona carpetas vacías (no tiene concepto de carpeta, solo de archivo), así que sin este archivo la carpeta nunca llega a GitHub y puede perderse en local sin dejar rastro. Regla derivada: **nunca usar `git clean -fd` ni `git reset --hard` como "deshacer" genérico** — ambos borran todo lo no confirmado sin distinguir entre el error puntual que se quiere revertir y otros cambios legítimos aún no commiteados (incluidas las carpetas vacías recién creadas). Antes de un revert destructivo: `git status` para ver qué se va a tocar, y `git clean -fdn` (dry-run) antes de `git clean -fd`.
